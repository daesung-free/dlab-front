## 작업 규칙

- **한 묶음 = PR 하나.** 화면마다 PR을 쪼개면 리뷰가 파편화된다.
- **`src/pages/screens/StudentSearch.tsx`를 본뜬다.** 목록 화면에 필요한 게 전부 들어 있다.
- 시작 전에 `CLAUDE.md`의 **3. API 연동 규약**을 읽는다. 모르면 반드시 틀리는 것 5가지가 있다.
- 붙일 화면의 **`docs/API_GAPS.md` 2부 항목을 먼저 확인**한다. 필드가 모자란 화면이 있다.

### 화면 하나를 "끝났다"고 하려면

- [ ] 목록이 실제 데이터로 나온다
- [ ] 검색조건이 **실제로 서버에 전달된다** (안 먹는 조건은 화면에서 빼거나 API_GAPS에 적는다)
- [ ] 페이징·정렬을 **엔드포인트에 맞게** 골랐다
  - 서버가 `page`·`size`·`sort`를 받으면 → `useServerTable` + `serverPaging`
  - 서버가 결과를 통째로 주면(출결·사유신청·상벌점·상담·루틴) → `useServerData`,
    `serverPaging`을 넘기지 않아 `DataTable`의 클라이언트 페이징·정렬로 돈다.
    비페이징 응답에 `useServerTable`을 쓰면 페이저와 정렬 헤더가 통째로 죽는다
- [ ] 정렬 UI가 **서버가 받는 키에만** 붙어 있다 — 그 밖은 조용히 무시된다
      (클라이언트 정렬로 도는 화면은 전량이 있으므로 이 제약이 없다)
- [ ] 지점 파라미터(`academyId`)를 넘긴다. 못 고른 상태면 `enabled: false`
- [ ] 마스킹이 서버 `masked`를 우선한다
- [ ] 로딩·에러가 보인다
- [ ] **목업 컬럼을 임의로 지우지 않았다.** 못 채운 건 `API_GAPS.md`에 적었다

- 출결의 '사유 승인'은 상태가 아니라 **`excused` 플래그**다. 다른 상태와 함께 고르면 AND로 걸린다
- 출결 헤더의 날짜 버튼(`2026-05-28 ▾`)을 뺐다. 조회 기간이 검색폼에 이미 있고,
  `Mockup.actions`는 상태를 못 가져 날짜가 하드코딩으로 굳는다

**백엔드 요청 → 반영 완료** (2026-09-03 확인 · API_GAPS 6부에 전문)

상벌점 '반'·'재원 상태', '방식'의 반복 파라미터, 일괄 부여 **일자 입력**(목업 원형 복원),
출결 **기간 조회**가 전부 들어왔다. 사유신청 탭 건수도 서버 `summary` 기준으로 옮겼다.

**남은 것 2개** — 둘 다 "그대로 두는 게 맞다"로 정리된 건이다.

| 항목 | 상태 |
|---|---|
| 출결 '알림' 컬럼 | 발송 자체가 E-5·E-7 대기라 `<Unfilled/>` 유지. **재요청하지 말 것** |
| 사유신청 '벌점 확정 충돌' 타일 | 요구사항(F-4.1-6·A-6)에 있는 항목이고 미정인 건 확정 시점(I-10)뿐. 회색 타일 유지 |

**★ 기간 조회가 열리면서 바뀐 것** — 출결을 기간으로 조회하면 **학생 × 날짜로 행이 늘어난다**
(19명 × 3일 = 57행). 행 키가 `date:enrollmentId`이고, 기간일 때만 '일자' 컬럼이 붙는다.
`summary.total`도 학생 수가 아니라 학생 × 일수 합이다.

**★ 페이징 — 전환에 순서가 있다**
- **출결은 안 연다**(재원생 전원이 목적). 클라이언트 모드로 **확정**
- **상벌점·사유신청은 열린다.** 단 **백엔드가 넣고 알린 뒤에** 옮긴다 —
  그전에 `useServerTable`로 바꾸면 `meta`가 없어 **목록이 통째로 빈다**
- 전환 시 사유신청의 **탭 건수**도 같이 옮겨야 한다(지금은 기간 전량에서 센다).
  `summary`는 페이징 후에도 필터 전체 기준이라 상단 통계는 손댈 필요가 없다
