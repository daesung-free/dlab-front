## 1-1. ✅ 해결됨 — 최상위 관리자가 차단되던 문제

> **검증 (2026-09-01, 커밋 `79a51d0`)**
> ```
> GET /attendance?date=2026-09-01&academyId=8   (admin/SUPER_ADMIN)  → 200, rows 20건
> GET /attendance?date=2026-09-01               (academyId 없음)     → 400 "지점을 지정해야 합니다"
> ```
> 차단됐던 8개(`attendance`, `penalties`, `penalties/items`, `absence-requests`,
> `consults`, `consults/status`, `consults/tags`, `student-signups`) **전부 정상 동작 확인**.
>
> 지점 관리자 쪽 방어도 같이 확인했다 — `branch`(분당) 계정이 `academyId=1`(이매)을 보내면
> `OTHER_BRANCH_ACCESS_DENIED`로 막히고, 안 보내면 자기 지점이 나온다. **의도대로다.**
>
> 프론트 규칙: **전 지점 권한 계정은 지점 선택 UI가 필수다.** 안 고르면 화면이 400으로 비어 보인다.

> 요청: 이 8개에 `academyId` 쿼리 파라미터를 열고, **전 지점 권한자일 때만** 허용할 것.
> (지점 권한자가 보내면 무시하거나 403 — 지금 `/students`의 `SearchScope` 방어는 그대로 유지)

## 1-2. ✅ 해결됨 — OpenAPI 스펙이 실제와 다르던 문제

> **검증 (커밋 `b94b611`)** — 21개 엔드포인트가 가리키던 잘못된 타입이 정리됐다.
> ```
> POST /api/v1/admin/classes  requestBody → #/components/schemas/ClassCreate   (전: 방화벽 스키마)
> /attendance 응답 → AttendanceRowResponse (전: 상벌점 RowResponse)
> ```
> 충돌 원인이던 일반 이름(`Create`, `Item`, `Detail`, `Row`, `RowResponse`, `ItemResponse`)이
> **스펙에서 전부 사라졌다**. 스키마 478종.
>
> `npm run api:types` 재생성 완료 — `src/api/schema.d.ts`. 생성된 타입이 실제 응답과 일치하는 것을
> `StudentResponse`·`AttendanceRowResponse`로 확인했다.

<details><summary>원래 보고 내용</summary>

### (해결 전) OpenAPI 스펙의 응답이 실제와 다르다

`/v3/api-docs`가 **틀린 스키마**를 준다. 중첩 record 이름이 겹치는데 springdoc이 하나로 합쳐버린다.

실제 확인 (BRANCH_ADMIN으로 호출):

| 엔드포인트 | 스펙이 말하는 필드 | **실제 응답 필드** |
|---|---|---|
| `/attendance` | `occurredAt, category, itemName, point, grantedBy` (상벌점 필드) | `enrollmentId, studentNo, name, className, seatCd, checkInAt, checkOutAt, status, excused, studyMinutes, studyTime, guardianPhone, unexcusedLate` |
| `/absence-requests` | 위와 동일 (상벌점 필드) | `id, approvalRequestId, submittedAt, studentNo, name, className, type, period, reason, approverType, status, escalationCandidate` |
| `/meals/orders` | 위와 동일 (상벌점 필드) | `id, mealDate, mealType, canceledAt, cancelPath` |
| `/routines` | 특강(`lectureType, capacity, fee`) 필드 | 루틴 필드 |

겹치는 이름이 **25개 이상**이다 (`Create` 7회, `Item` 5회, `Detail`·`Update` 4회, `RowResponse`·`Submit` 3회 …).

**영향**
- `npm run api:types`로 만든 타입이 **조용히 틀린다.** 컴파일은 통과하고 런타임에 `undefined`가 된다.
- Swagger UI의 요청/응답 예시도 같은 이유로 틀리다. 지금은 **문서를 믿을 수 없어 매번 실제 호출로 확인해야 한다.**

> 요청: 중첩 record에 `@Schema(name = "AttendanceRowResponse")`처럼 고유 이름을 주거나,
> springdoc이 바깥 클래스명을 접두어로 붙이도록 설정할 것. 프론트 타입 생성의 전제 조건이다.

</details>

## 1-3. ✅ 해결됨 — 정렬이 조용히 무시되던 문제

> **검증 (2026-09-01, 커밋 `f24f18f`)**
> ```
> ?sort=name,asc               → 강민주, 강민주, 강서연, 강서연
> ?sort=name,desc              → 한하윤, 한수빈, 한민주, 최현준
> ?sort=grade,asc&sort=name,asc → HIGH2 묶음 안에서 이름순 (다중 정렬 동작)
> ?sort=admissionDate,desc     → 반영됨
> ```
> 허용 필드: **`studentNo` · `name` · `grade` · `track` · `enrollmentStatus` · `admissionDate`**
> (`name`은 `student.name`으로 보내도 된다). 마지막에 학번을 tie-breaker로 붙여 페이징이 흔들리지 않는다.
>
> ⚠️ **남은 것 2가지 — 프론트가 알아야 한다**
> - **반(`className`) 정렬은 아직 안 된다.** 목업의 '반' 정렬 컬럼은 켜면 안 된다.
> - **허용 밖 필드는 400이 아니라 조용히 무시**되고 기본 정렬(학번)로 떨어진다
>   (`?sort=nonsense,asc` → 200). 백엔드가 의도한 동작이지만, 오타 하나가 화면에서는
>   "정렬이 안 걸리는" 증상으로만 보인다. **프론트는 위 6개 목록을 코드에 고정해두고
>   그 밖의 컬럼에는 정렬 UI를 붙이지 않는다.**

### (해결 전) 정렬이 조용히 무시된다

```

> 요청: `pageable.getSort()` 반영. 어렵다면 지원 정렬키를 정하고 **그 외에는 400**을 낼 것.
> 조용히 무시하는 것이 가장 나쁘다.

## 1-4. ✅ 해결됨 — `month` 형식 불일치

> **검증 (커밋 `e008ba9`)** — 전 엔드포인트가 `yyyy-MM`으로 통일됐다.
> ```
> /meals/monthly?month=2026-09      → 200
> /routines?month=2026-09           → 200   (전: 400, 정수만 받았다)
> /schedules?month=2026-09          → 200
> /tuition/fee-table?month=2026-09  → 200
> ```

같은 이름인데 형식이 갈리고, 틀리면 **500**이 난다.

| 엔드포인트 | 형식 | 반대로 넣으면 |
|---|---|---|
| `/meals/monthly`, `/meals/closures` | `2026-09` (YYYY-MM) | 500 |
| `/routines`, `/schedules`, `/tuition/fee-table` | `9` (1~12 정수) | 500 |

> 요청: 하나로 통일. `YYYY-MM` 문자열을 권한다 — 연도를 따로 안 보내도 되고 오해가 없다.

## 1-5. ✅ 해결됨 — 타입 오류 400

> **검증 (2026-09-01, 커밋 `aef8a5b`)**
> ```
> ?year=abc   → 400 "파라미터 'year' 값이 올바르지 않습니다: abc"
> ?grade=XXX  → 400 "파라미터 'grade' 값이 올바르지 않습니다: XXX (허용값: HIGH2, HIGH3, N_SU, STAFF)"
> ```
> enum 허용값이 응답에 실려서 프론트가 원인을 바로 안다. **여기까지는 해결.**
>
> ✅ **추가로 보고했던 500 잔존 경로도 해결됐다** (커밋 `ff5cb76`)
> ```
> GET /meals/monthly?academyId=8&month=9
>   → 400 "파라미터 'month' 값이 올바르지 않습니다: 9"   (전: 500 INTERNAL_ERROR)
> ```
> <details><summary>원래 보고 내용</summary>
>
> ```
> GET /meals/monthly?academyId=8&month=9   → 500 INTERNAL_ERROR
> ```
> ```
> java.time.format.DateTimeParseException: Text '9' could not be parsed at index 0
>   at AdminMealController.monthly(AdminMealController.java:60)
> ```
> 원인: 이 컨트롤러는 `month`를 **String으로 받아 메서드 안에서 `YearMonth.parse()`** 한다.
> 새 핸들러는 스프링 바인딩 단계의 `MethodArgumentTypeMismatchException`을 잡는데,
> 이건 바인딩을 통과한 뒤 메서드 본문에서 터지므로 안 걸린다.
> 같은 패턴이 `AdminMealController` 4곳(60·72·126·144행), `AppDailyReportController` 1곳(66행)에 있다.
>
> > 요청: `YearMonth`를 파라미터 타입으로 직접 받거나(`@DateTimeFormat`),
> > `DateTimeParseException`도 400으로 잡을 것.
> </details>

<details><summary>원래 보고 내용</summary>

### (해결 전) 잘못된 타입의 파라미터가 400이 아니라 500이다

```
GET /api/v1/admin/students?year=abc   → 500 INTERNAL_ERROR "서버 오류가 발생했습니다."
```

`MethodArgumentTypeMismatchException`이 `GlobalExceptionHandler`에 없어 그대로 500이 된다.

- 프론트 입장에서 **내 요청이 잘못된 건지 서버가 죽은 건지 구분할 수 없다.** 재시도 여부 판단이 안 된다.
- 운영에서 잘못된 링크·오래된 북마크 하나가 500 알람을 만든다.

> 요청: 타입 불일치는 400 + 어떤 파라미터가 잘못됐는지 메시지에 포함.

</details>

## 1-6. ✅ 통일됨 — 목록 응답 형태

> **검증** — `/students`가 `data + meta` 형태로 바뀌었다.
> ```json
> { "success": true, "data": [ … ], "meta": { "page":0, "size":3, "totalElements":60, "totalPages":20, "hasNext":true } }
> ```
> 프론트 `requestPaged()`는 두 형태를 모두 흡수하도록 만들어둬서 코드 변경 없이 그대로 동작했다.

<details><summary>원래 보고 내용</summary>

### (통일 전) 목록 응답 형태가 두 가지다

```
ApiResponse.from(page)    → { data: [...],                 meta: {page,size,totalElements,...} }
ApiResponse.success(page) → { data: { content:[...], number, totalElements, ... } }   ← /students
```

프론트는 `requestPaged()`에서 둘 다 흡수하도록 만들어뒀다. 다만 새 엔드포인트를 만들 때마다
확인이 필요하므로, 통일하면 양쪽 모두 편해진다.

</details>

# 2부. 화면별 대조

## 2-1. API가 아예 없는 화면 (6개) ★

붙일 엔드포인트 자체가 없다. 목업만 있고 서버에 대응 도메인이 없다.

| 화면 | 코드 | 화면이 필요한 것 | 그나마 가까운 것 |
|---|---|---|---|
| 대기자 관리 | F-4.2 | 입학예약 파이프라인(단계·전환·이력) | 없음. `student-signups`는 앱 가입 승인이라 다른 것 |
| 신상기록부 | F-4.11-9 | 폼 정의·작성 현황·제출 내용 | `consults/status.profileWritten` (작성 여부 boolean 하나뿐) |
| 실적 관리 | F-4.10-6 | 합격 대학·학과·전형·등록확정 | 없음 |
| Daily Report 집계 | F-4.11-6 | 학생별 순공/재실/집중도/루틴이행 **집계 + 순위** | `/statistics`(전체 개요), `/learning-plans/.../statistics`(학생 1명) |
| 금일 수정 이력 | F-C-1 | 전 업무영역 감사 로그(수정자·전후값·IP) | `/branch-configs/{id}/history`(지점설정 전용), `/students/{id}/status-logs`(상태변경 전용) |

## 4-2. "미배정" 조건이 없다 ★

출결이 재원생 전원을 주는 것은 의도된 설계다(결석자를 세야 한다). 문제는 **나중**이다.

- 지금 대응: `useServerData`(신규)로 받아 `DataTable`의 클라이언트 페이징·정렬로 돈다.
  전량이 손에 있으므로 클라이언트 정렬이 틀리지 않는다
- ⚠️ **여기에 서버 페이징이 생기는 순간 화면이 조용히 틀린다.** 한 페이지만 정렬해놓고
  전체가 정렬된 것처럼 보이게 된다 — 에러도 안 나고 눈에도 안 띈다
- 요청: 열 계획이 있는지만 알려줄 것. 있으면 프론트가 지금 `useServerTable`로 붙여둔다.
  없으면 클라이언트 모드로 확정한다

### ✅ 답변 — 출결은 안 열고, 나머지 둘은 순서가 있다

- **출결은 안 연다.** 재원생 전원을 주는 것이 목적이고 지점당 300명 규모까지 그대로 간다
  → 클라이언트 모드로 **확정**. `src/api/attendance.ts` 주석에 확정으로 적어뒀다
- **상벌점·사유신청은 연다.** 다만 **백엔드가 먼저 넣고 알린 뒤에** 프론트가 옮긴다 —
  그전에 `useServerTable`로 바꾸면 응답에 `meta`가 없어 **목록이 통째로 빈다**
- 페이징이 들어가도 `summary`는 페이지 합계가 아니라 **필터 전체 기준**을 유지한다
  → 상단 통계 타일은 전환할 때 손댈 필요가 없다
- ⚠️ 전환할 때 같이 옮겨야 하는 것: 사유신청 화면의 **탭 건수**. 지금은 기간 전량에서 세는데,
  페이징이 들어오면 서버 `summary`나 별도 호출로 옮겨야 한다(현재 `summary`에는 `pending`만 있다)

## 6-2. 출결이 하루 단위 조회만 된다

`date` 파라미터 하나뿐이라 기간 조회가 안 된다. 목업 검색조건은 '조회 기간'(범위)이다.

- 지금 대응: 시작일만 보내고, 기간을 고르면 화면이 "하루 단위로만 조회됩니다"를 띄운다
- 요청: `from`·`to`를 받거나(다른 두 엔드포인트는 이미 그렇다), 화면을 하루 단위로 확정할 것

## 6-3. 상벌점 응답에 `className`이 없다

목업의 '반' 컬럼이 못 채워져 `<Unfilled/>`로 뒀다. 같은 화면의 반 **필터**(`classId`)는
서버가 받는데 결과 행에는 반이 없어, 반으로 걸러놓고 어느 반인지 표에서 확인이 안 된다.

## 6-4. 상벌점에 '재원 상태' 검색조건이 없다

목업 조건은 전체보기 / 재원생 / 퇴원생 3종인데 `/penalties`가 안 받는다.
응답 행에도 재원 상태가 없어 화면에서 거를 수도 없다. 지금은 조건을 걸면
"서버가 아직 받지 않습니다" 안내를 띄운다.

## 6-5. 상벌점 '방식' 필터가 화면과 축이 다르다

서버 `source`는 `KIOSK`·`ROUTINE`·`MANUAL` **단일값**이고, 화면은
수기(MANUAL) / 자동(KIOSK+ROUTINE) 둘로 묶는다. '자동'은 두 값의 OR 라 단일 파라미터로 못 보낸다.

- 지금 대응: 수기만 고른 경우만 `source=MANUAL`로 보내고, 나머지는 화면에서 거른다
  (전량이 오므로 결과는 같다)
- 요청: `source`를 반복 파라미터로 받아줄 것. `?source=KIOSK&source=ROUTINE`

## 6-6. 상벌점 부여에 일자가 없다

`POST /penalties`의 본문은 `enrollmentIds`·`itemId`·`reason` 뿐이고 `occurredAt`은
서버가 현재 시각으로 찍는다. 목업의 일괄 부여 패널에는 **일자 입력이 있다** —
어제 일을 오늘 입력하는 경우가 실제로 있다.

- 지금 대응: 일자 입력을 빼고 "부여 일자는 지금 시각으로 기록됩니다"를 명시했다
- 요청: 본문에 `occurredAt`(선택)을 받아줄 것

## 6-7. 사유 신청 '벌점 확정 충돌' 지표가 미지원이다

`summary.penaltyConflictUnavailable`로 미지원임을 알려주는 것 자체는 좋다.
다만 화면 상단 타일 하나가 값 없이 남는다(`<Unfilled/>`).

> 요청: 벌점 확정 여부 판정을 넣을지(I-10 기준 확정 필요), 목업에서 타일을 뺄지 결정.
> 타일 제거는 목업 수정이라 프론트 쪽 승인도 필요하다.

### ✅ 답변 — 타일은 유지한다

요구사항(F-4.1-6 · A-6)에 **"벌점 확정 후 승인 불가"**가 박혀 있고, 앱도 `is_penalty_finalized`로
승인 버튼을 막게 돼 있다. 미정인 것은 **확정 시점(I-10)** 하나뿐이라 목업을 고칠 건이 아니다.
→ 화면은 타일을 그대로 두고 회색(`<Unfilled/>`)으로 표시한다. **목업 수정 없음.**

## 6-8. 출결 '알림' 컬럼은 절반만 채워진다

응답의 `unexcusedLate`로 '무단지각'은 판단되는데, 목업의 '발송됨'은 **발송 이력 API가
없어** 판단할 수 없다(2-2의 F-4.4와 같은 건). 지금은 `<Unfilled/>`다.

### ✅ 답변 — 지금은 못 한다. 발송이 붙을 때 같이 나온다

발송 이력이 있어야 판단하는데 **알림 발송 자체가 E-5·E-7(문구·FCM) 대기**라
`notification_log`가 비어 있다. 이력 API만 먼저 만들어도 채울 값이 없다.
→ `<Unfilled/>` 유지. 재요청하지 말고 **E-5·E-7이 풀릴 때 같이 붙인다.**

## 6-9. 확인만 — 서버 상태값이 목업보다 하나 많다

`ScreenStatus`가 `ON_TIME`·`LATE`·`ABSENT`·`OUT`·**`EARLY_LEAVE`** 5종인데 목업 칩은
조퇴가 빠진 4종 + 사유승인이었다. **화면에 조퇴를 추가**했다(빼면 조퇴 건이 어느 칩·통계에도
안 잡혀 합이 `total`과 안 맞는다). BE 작업은 없고, 목업 변경 이력으로 남긴다.

또한 `EXCUSED`는 상태가 아니라 `excused` 플래그이므로 `statuses`에 넣으면 400이다.

```
GET /attendance?date=2026-09-02&academyId=8&statuses=EXCUSED
→ 400 "파라미터 'statuses' 값이 올바르지 않습니다: EXCUSED"
```

`summary`에는 `EXCUSED` 카운트가 함께 오는데, 상태와 직교하는 축이라
**5종 합계 + EXCUSED가 `total`을 넘을 수 있다**(지각이면서 사유 승인된 건). 화면에도 그렇게 적어뒀다.

## 6-10. 로컬 시드에 아직 없는 것

- **하원 태깅** — `checkOutAt`이 19건 전부 `null`이라 '하원' 컬럼과 순공시간 확정 경로를
  확인하지 못했다. 하원까지 있는 **과거 하루치**가 있으면 `/study-time/recalculate`도 같이 확인된다
  (오늘 날짜로 부르면 `{"updated":0}` — 당일은 대상이 아니라 정상이다)
- **보호자 전화 형식** — `010-2000001`로 자릿수가 한 칸 빈다. 마스킹 표시에만 영향 간다

# 7부. 묶음 D 연동 중 확인된 것 (2026-09-03)

## 7-1. `IssueMonthly.discountRate` 를 생략하면 400 ★

```
POST /admin/tuition/billings/monthly
{"enrollmentId":1,"month":"2026-09","seatType":"GENERAL"}
  → 400 "요청 본문 형식이 올바르지 않습니다."

{"enrollmentId":1,"month":"2026-09","seatType":"GENERAL","discountRate":0}
  → 200
```

`discountRate` 가 **primitive `int`** 라(`Integer` 가 아니라) 값이 없으면 역직렬화가 깨진다.
스펙의 `required` 에는 없어서 **선택값으로 보이는데 실제로는 필수**다.

- 메시지가 "요청 본문 형식이 올바르지 않습니다"라 **어느 필드가 문제인지 알 수 없다.**
  실제로 스펙대로 보냈는데 막혀서 원인을 찾는 데 시간이 걸렸다
- 같은 패턴이 다른 요청에도 있는지 확인이 필요하다(`int`/`long`/`boolean` primitive 필드)

> 요청: `Integer` 로 바꿔 기본값 0을 서버가 채우거나, `required` 에 넣어 스펙과 실제를 맞출 것.

## 7-2. 수납현황에 결제 '거래' 축이 없다

`RowView` 는 청구 단위(누가 얼마 청구받고 얼마 냈나)만 준다. **언제 무엇으로 냈는지가 없다.**

| 목업 컬럼 | 상태 |
|---|---|
| 결제일자 | 없음 |
| 전표번호 | 없음 |
| 결제수단 | 없음 (카드/가상계좌/현금 집계도 못 그림) |
| 지점 | 행에는 없음. 조회가 지점 단위라 헤더로는 표시 가능 |
| 청구기수 | 없음 |

화면 상단 통계에서 **결제수단별 집계 3칸이 못 그려진다.** 지금은 청구 총액·수납률로 대체하고
결제수단 칸은 `<Unfilled/>` 로 뒀다.

> `POST /billings/{id}/payments` 로 수단을 받아 저장은 하고 있으니 데이터는 있을 것이다.
> 조회 응답에 거래 목록(또는 최근 결제 정보)을 실어주면 된다.

## 7-3. 할인 정책 API가 없다

수납현황의 세 번째 탭(할인 정책·청구액 계산)에 대응하는 엔드포인트가 없다.

- `IssueMonthly` 가 `discountRate` 를 받긴 하지만 **호출할 때 넘기는 값**이지 저장된 정책이 아니다

  프론트가 계산한 금액을 결제창에 넘기면 금액을 조작할 수 있다
- 지금 대응: 그 탭은 목업 그대로 두고 화면에 안내를 띄웠다

## 7-4. 특강 신청 기간(`applyFrom`/`applyTo`)이 `Instant` 다

{"applyFrom":"2026-09-01T00:00:00"}   → 400 "요청 본문 형식이 올바르지 않습니다."

`RosterRow`: `applicationId, studentId, studentNo, studentName, status, waitlisted, appliedAt, memo`

## 7-7. 배식 태깅 로그를 관리자가 조회할 수 없다 ★

급식 화면의 세 축 중 하나가 **배식 체크**(신청한 사람이 실제로 먹었는가)인데,

> 배식 줄을 세워둘 수 없으므로 관리자가 즉시 수기 확인으로 통과시키고,
> **그 건을 나중에 되짚을 수 있도록 사유와 처리자를 남긴다.**

즉 **수기 확인은 예외가 아니라 정상 경로**이고, 그걸 되짚는 화면이 이 탭이다. 조회가 없으면
"오늘 몇 명이 수기로 통과했는지"를 아무도 모른다.

> 요청: `GET /admin/meals/servings?academyId=&date=` 같은 조회.
> 필요한 것 — 시각 · 학생 · 방식(QR/수기) · 단말 · 결과(정상/중복/미신청) · 수기 사유 · 처리자.

`PUT /admin/meals/policy` 는 있는데 **GET이 없다.** 현재 마감일(deadlineDays)이 며칠인지
화면이 알 수 없어, 정책 탭이 값을 표시하지 못한다.

# 8부. 신규 접수 등록 (2026-09-03)

## 8-1. 등록 요청(`Admit`)이 폼보다 훨씬 얇다 ★

`Admit` 이 받는 것: `academyId, year, name, grade, track, phone` — **6개뿐**이다.
등록 폼은 그보다 훨씬 많은 값을 받는다.

| 폼 값 | 저장 방법 |
|---|---|
| 생년월일 · 성별 · 출신학교 · 주소 | `PATCH /students/{id}` 로 **한 번 더** 보내야 한다 |
| 영문명 · 학부모 연락처 · 졸업연도 | **넣을 곳이 없다** |
| 등원일(`admissionDate`) | **넣을 곳이 없다.** 서버가 등록일(오늘)로 자동 설정한다 |
| 반 · 좌석 · 사물함 · 장학 | 각자 전용 API. 등록 후 해당 화면에서 처리 |

**저장이 두 번 나가는 것이 문제다.** ①이 성공하고 ②가 실패하면 **학생은 이미 등록된 상태**인데
화면이 "저장 실패"로만 알리면 담당자가 다시 등록해 **중복 학생**이 생긴다.

- 지금 대응: 부분 성공을 별도 상태로 구분해 *"학생은 등록됐지만 상세 저장이 실패했습니다 —
  다시 등록하지 마세요"* 라고 학번과 함께 표시한다
- 요청: `Admit` 에 `birthDate·gender·schoolName·address·admissionDate` 를 받아 **한 번에 끝내기**.
  `StudentUpdate` 가 이미 그 필드들을 받고 있으니 같은 값을 등록에서도 받으면 된다

## 8-2. 등원일을 지정할 수 없다

`admissionDate` 는 조회 응답에 있는데 **등록·수정 어디에도 없다.** 서버가 등록 시점으로 정한다.

중도 입학·소급 등록(이미 다니던 학생을 나중에 시스템에 넣는 경우)에서 실제 등원일과
데이터가 어긋난다. 교습비 일할 계산(`remainingDays`)이 등원일 기준이라면 금액에도 영향이 간다.

## 8-3. 다음 학번을 미리 볼 수 없다

목업은 "다음 학번은 2026-0048입니다"를 보여줬는데, **채번 미리보기 API가 없다.**
(예전 목업은 목데이터로 지어낸 값이었다 — 실연동하면서 뺐다.)

없어도 동작에는 지장이 없다. 다만 "저장하면 몇 번이 되는지" 를 미리 보여주는 UX였으므로,
필요하면 `GET /students/next-no?academyId=&year=` 같은 것이 있으면 된다. **우선순위 낮음.**

# 9부. 승인 라우팅 (2026-09-03)

## 9-1. 진행 중인 승인 요청을 관리자가 볼 수 없다 ★

`GET /admin/approvals` 가 `@PreAuthorize("hasRole('TEACHER')")` 다 — 주석도
*"내가 담당선생님인 승인 대기 목록"* 이라고 적혀 있다.

```
admin (SUPER_ADMIN)  → 403 FORBIDDEN
branch (BRANCH_ADMIN) → 403 FORBIDDEN
```

담임의 개인 대기열로는 맞는 설계다. 다만 **관리자 화면에는 대응하는 조회가 없다.**

- 승인 라우팅(F-4.11-5)은 관리자가 "지금 승인이 몇 건 밀렸는지" 를 봐야 하는 화면이다
- 사유 신청 관리(F-4.1-5)와도 같은 스키마를 공유한다고 목업 주석에 적혀 있다
- 지금 대응: 항목 설정 매트릭스만 붙이고, 진행 중 목록은 화면에 "담임 전용 API" 라고 안내

**2026-09-07 재확인 — 아직 안 열렸다.** 스펙에서 `parameters` 가 비어 있어 제한이
풀린 걸로 잠깐 오인했는데, `summary` 는 그대로 *"내가 담당선생님인 승인 대기 목록"* 이고
본사·지점 계정 모두 여전히 403 이다. **파라미터 유무로 권한 변경을 판단하면 안 된다 —
계정별로 실제 호출해 봐야 한다.**

> 요청: 지점 단위 승인 요청 조회(관리자 권한). 필요한 것 —
> 유형 · 학생 · 신청 시각 · 현재 승인자 · 에스컬레이션 예정 시각 · 상태.

## 9-2. 승인 대상 신청 유형이 3종뿐이다

서버 enum: `ABSENCE_REASON` · `REGULAR_SCHEDULE` · `FIREWALL_UNLOCK`

목업은 10종이었다 — 결석·지각·조퇴·외출·정기일정·좌석 이탈·급식 취소·질의응답 예약·
방화벽 해제·전자기기 반입.

차이가 나는 이유는 두 가지로 보인다.
- **묶인 것**: 결석·지각·조퇴·외출이 `ABSENCE_REASON` 하나로 합쳐졌다
- **승인 도메인 밖**: 좌석 이탈·급식 취소·질의응답 예약은 각자 다른 방식으로 처리된다
  (목업도 그것들을 `AUTO`로 표기했었다)

> 확인 필요: **전자기기 반입**은 목업에도 "항목 존재 여부부터 확인 필요"로 남아 있던 항목이다.
> I-12(항목별 승인 주체 매트릭스) 종결 시 3종이 맞는지 같이 확정할 것.

## 9-3. (확인만) `configured=false` 의 의미

응답 주석이 명확하다 — **`false` 면 그 유형의 신청이 거절된다.**
"아직 안 정했다"가 아니라 **동작에 영향이 있는 상태**라, 화면에서 미설정을 눈에 띄게 표시하고
통계 칸도 "주체 미지정" → **"신청이 거절됨"** 으로 바꿨다.

# 10부. 설문 관리 (2026-09-03)

## 10-0. ⚠️ 로컬에서 겪은 것 — 실행 중인 백엔드가 옛 빌드였다

설문 개설이 **유효한 요청에도 500**이 나서 한참 원인을 찾았다. 결론은 API 결함이 아니라
**8080에 떠 있던 프로세스가 옛 빌드**였던 것이다.

```
8080 (실행 중이던 것)          → INTERNAL_ERROR
8099 (현재 소스로 새로 빌드)     → 성공
```

같은 DB를 보고 있어서 **목록에는 보이는데 생성만 안 되는** 상태라 더 헷갈렸다.
백엔드를 재시작하니 8080에서도 정상 동작했다.

> 교훈: 이유를 알 수 없는 500이 특정 엔드포인트에서만 나면 **먼저 백엔드를 재시작**해 볼 것.
> 프론트가 "API 버그"로 보고하기 전에 확인하는 편이 빠르다.

## 10-1. 템플릿 관리 API가 없다

목업의 '템플릿' 탭(템플릿 목록·생성·사용횟수·인스턴스화)에 대응하는 엔드포인트가 없다.
`survey_templates` 테이블은 스키마에 있는데 관리자 API가 없다.

목업 주석이 이 관계를 이렇게 정의하고 있다 — **참조가 아니라 복제**다.
템플릿에서 설문을 만들면 문항이 스냅샷으로 복사되고, 나중에 템플릿을 고쳐도 이미 배포된
설문은 안 바뀐다(응답이 "그때 그 문항"에 묶여 있어야 집계가 안 깨진다).

> 지금 대응: 템플릿 탭은 목업 그대로 두고 저장 버튼을 비활성화했다.

## 10-2. 설문에 상태 필드가 없다 ✅ 반영됨 (2026-09-07)

`status` 가 들어왔다 — `SCHEDULED`(아직 안 열림) · `OPEN` · `CLOSED`.
화면이 `closesAt` 과 현재 시각을 비교하던 걸 걷어냈다. 브라우저 시계가 어긋나면
같은 설문이 사람마다 열려 보이고 닫혀 보이던 문제가 없어졌다.

`SCHEDULED` 는 화면에 없던 상태다 — '예정' 으로 표시한다.

⚠️ **조기 마감은 `closesAt` 을 지금으로 당기는 방식이라 원래 마감 시각이 덮어써진다.**
"예정 마감이 언제였나"는 남지 않는다. 지금 화면이 그 값을 쓰진 않지만,
나중에 마감 이력을 보여줘야 하면 서버에 별도 컬럼이 필요하다.

- 목업의 '작성중'(초안) 상태는 여전히 서버에 없다. 개설하면 바로 배포된다

## 10-3. 문항 유형이 화면보다 적다

| 화면 | 서버 |
|---|---|
| 객관식(단일) | `SINGLE_CHOICE` |
| 객관식(복수) | `MULTI_CHOICE` |
| 주관식 | `TEXT` |
| 점수 입력 | `NUMBER` |
| **척도(1~5)** | 없음 — 선택형으로 내려보낸다 |
| **과목별 점수** | 없음 — 선택형으로 내려보낸다 |

척도는 선택형으로 보내도 집계가 되지만(보기별 분포), **평균을 못 낸다.**
과목별 점수는 가채점 전용이라 `GRADE_INPUT` 유형과 함께 확인이 필요하다.

## 10-4. 원시 응답 다운로드가 없다

집계(`/results`)는 있는데 **응답 원본을 내려받는 API가 없다.** 목업에 버튼이 있어
비활성으로 뒀다. 가채점처럼 개별 응답을 봐야 하는 설문에서는 집계만으로 부족하다.

백엔드가 1~10부에서 요청한 것들을 한 번에 정리했다. **실제 호출로 전부 확인**하고 프론트에 반영했다.

## 해결된 것 — 프론트에서 걷어낸 임시 처리

| 백엔드 수정 | 프론트에서 없앤 것 |

## 반영하면서 알게 된 것

**`missingDays` 는 `countedDays` 와 함께 봐야 의미가 있다.** 분모를 모르면 "3일 미작성"이
많은 건지 알 수 없어, 표에 `3 / 7일` 형태로 함께 그린다.

**루틴 매트릭스의 `status=null` 은 미제출과 다르다.** "아직 입력 안 한 칸"이라
이행률 분모에서 빼야 한다 — 안 그러면 입력 전 학생이 전부 0%로 보인다.
행에 칸이 아예 없는 것(그 루틴 대상이 아님)과도 구분해서 그린다.

**수납 `payments[]` 는 취소분이 빠져 있다**(서버 주석). 그래서 결제수단 집계가
"지금 실제로 결제된 수단"과 맞는다. 한 청구에 결제가 여러 건일 수 있어(부분납)
컬럼은 마지막 거래를 대표로 보여주고 건수를 함께 표시한다.

**`pgTid` 는 비어 있을 수 있다.** 가상계좌·현금은 PG 거래번호가 없다 — 전표번호 컬럼이
`-` 로 나오는 것이 정상이다.

## 남은 것

- **이석 위치** — 좌석 이탈 로그 수집이 보류라 미포함. 좌석배치표·좌석이탈 화면 2곳
- **특강 수납 여부** — 특강비 청구 발행 경로 자체가 없어 미포함
- 그 밖에 1~10부에서 아직 안 닫힌 항목들(승인 요청 관리자 조회, 설문 템플릿·상태,
  배식 태깅 로그, 할인 정책)
  — `/students` 의 `academyId` 와 재수 구분은 2026-09-07 반영됐다

# 12부. 성적 관리 (2026-09-04)

> **정정 (2026-09-07)** — 12-1·12-2를 처음에 잘못 적었다.
> 백엔드 `CLAUDE.md`(커밋 `e2c0003`)에 **0826 회신으로 이미 닫힌 사항**이 정리돼 있는데
> 그걸 안 보고 "확인 필요"로 올렸다. 아래는 회신 기준으로 고친 것이다.

## 12-0. ✅ 반영됨 (2026-09-07) — 직원 수정 경로가 열렸다

```
PUT /admin/students/{enrollmentId}/grades/school-record   {"mainSubjectAverage":2.4}
PUT /admin/students/{enrollmentId}/grades/exam-scores      {"scores":[...]}
```

응답에 `modifiedBy`·`modifiedAt` 이 붙는다 — **null 이면 학생이 낸 그대로, 값이 있으면
직원이 고친 것**이다. 장학 취소 판정 근거라 화면에 구분해 표시한다.

실측에서 확인한 것 두 가지:

- **제출 이력이 없는 학생에게 PUT 하면 새로 만든다.** 직전 GET 이 404
  (`GRADE_SUBMISSION_NOT_FOUND`)였는데 PUT 은 200이었다. 수정 경로가 생성도 겸한다
- 모의고사는 **보낸 회차만 교체**된다. 회차를 지우는 수단은 아니다

**남은 것 ❌ — `modifiedBy` 가 직원 id(숫자)로만 온다.** 화면에 "누가 고쳤는지"를
쓰려면 이름이 필요한데 직원 조회 API가 없다. 지금은 "직원 수정" 과 날짜만 표시한다.

> 요청: `modifiedByName` 을 함께 싣거나, 직원 id → 이름 조회를 열어줄 것.

**미착수 — 표에 입력칸이 없다.** 목업이 조회 화면이라 수정 UI 추가는 승인 사항이다(CLAUDE.md 1).
API는 준비됐으므로 승인되면 붙인다.

## 12-1. 학생이 입력한 성적을 **직원이 수정할 경로**가 없다 — ✅ 해결 (12-0 참고)

입력 주체는 **확정돼 있다**(2026-08-26 회신). 대리 입력 여부를 물을 사항이 아니었다.

> 회신 원문: *"처음 입력시 학생, 이후 수정시에는 직원을 통해서 가능하도록"*

즉 **처음 입력 = 학생(앱)** 은 지금 구조가 맞다. 문제는 **뒤쪽**이다 —
수정이 직원을 거쳐야 하는데 `/api/v1/admin/**` 에 성적 수정 경로가 없다.
관리자는 조회만 가능하다.

이게 그냥 편의 기능이 아닌 이유: **장학 취소 판정이 이 등급을 근거로 돈다.**
학생이 잘못 넣은 값이 판정에 그대로 쓰이는데 고칠 사람이 없다.

> 요청: `PUT /admin/students/{enrollmentId}/grades` 같은 직원 수정 경로.
> 회신이 "직원을 통해서"라고 못박았으므로 **누가 고쳤는지도 남아야 한다.**

## 12-2. 외부 성적 연동·엑셀 업로드 — **요청 취소**

앞서 "더프리미엄 API 자동 조회·엑셀 업로드가 없다"고 적었는데, **둘 다 요청할 것이 아니었다.**

- **더프리미엄에서 6·9평을 못 받아온다**(0826 회신). 더프는 평가원 성적을 주지 않고,
  DSA에 입력된 평가원 성적을 더프 성적과 누적해 보여주는 구조다
- **엑셀 일괄 업로드는 우리가 제안했다가 채택되지 않은 안**이다. 학생 직접 입력이 확정됐다

목업 안내 문구(*"더프리미엄 API로 자동 조회… 엑셀 업로드로 반영"*)가 **옛 가정**이라
화면에서 그 문장을 걷어내야 한다 — 지금 화면은 그걸 `<Unfilled/>` 로 두고 있어
"언젠가 들어올 것"처럼 보인다.

## 12-2-a. 단원별 정답률은 출처 자체가 없다

엑셀 업로드가 없어지면서 단원별 정답률을 채울 경로가 사라졌다.
목업의 그 박스는 **삭제 대상인지 확인이 필요하다.**

## 12-3. (확인만) 화면이 열을 하드코딩하면 안 된다

`exam-forms` 가 과목 구성을 준다. 학년·연도마다 다르고 표시명도 바뀐다.

- `subjectCode`(통계 축)와 `subjectName`(표시명)이 분리돼 있다 — 표시명은 해마다 바뀌지만
  통계는 국어끼리 묶여야 하기 때문이다. **백분위 합 계산은 코드로 한다**
- `hasStandardScore=false` 인 과목(영어·한국사)은 표준점수 칸을 비운다. 절대평가라 값이 없다

## 12-4. (확인만) `examSkipped` 는 미입력이 아니다

**"모른다고 체크한 것"** 이다. 이때 `scores` 는 비고 `skipReason` 이 채워진다.
미입력과 같이 보여주면 담임이 "안 낸 학생"과 "모르는 학생"을 구분하지 못해,
화면에서 별도 안내로 갈랐다.
## 12-5. 0826 회신으로 함께 닫힌 것들 — 화면에 반영해야 할 사항

백엔드 문서에 정리된 확정 사항 중 **이 화면이 알아야 하는 것들**이다.

| 확정 | 화면 영향 |

| **가채점 원점수를 등급 환산하지 않는다.** 원점수 그대로 보관·표시 | 가채점 회차는 등급 칸이 아니라 **원점수**를 보여야 한다. 지금 화면은 등급 배지로만 그린다 |
| 탐구 사탐+과탐 교차 — **2026년까지 가능, 2027년부터 불가** | 과목 구성이 연도로 갈린다. 양식(`exam-forms`)이 연도별이라 자동 흡수되지만 확인 필요 |

| **평가원 성적은 두 번 처리된다** — 시행 당일분은 **학생에게 안 보이고 선생님에게만** | 관리자 화면에는 둘 다 보여야 하고, **어느 쪽인지 구분**돼야 한다. 지금 응답에 그 축이 없다 |
| 장학 신청 시 **성적표 원본 제출 필수**. 평가원 성적표는 문서번호가 없어 **"직원의 원본 확인 체크"** 로 대신한다 | 화면에 그 체크 UI가 필요하다. 응답에도 필드가 없다 |

## 12-6. 스키마에 없는 것 둘 (백엔드 문서 기준)

- **가채점 원점수** — 12-5의 "등급 환산 안 함"과 직결된다

# 13부. 메시지 관리 (2026-09-04)

## 13-1. 공지 수정이 부분 갱신을 안 받는다 ★

`PUT /admin/notices/{id}` 의 `title`·`content` 가 **필수**라, 상단 고정만 켜려 해도
전체 본문을 함께 보내야 한다.

```
PUT /notices/1  {"pinned":true,"banner":true}
  → 400 "content: 내용은 필수입니다., title: 제목은 필수입니다."

PUT /notices/1  {"title":"…","content":"…","pinned":true,"banner":true}
  → 200
```

**✅ 반영됨 (2026-09-07)** — `PATCH /notices/{id}` 가 생겼다. 보내지 않은 필드는 그대로다.
고정 버튼이 남의 본문 수정을 덮어쓰던 위험이 없어졌다. 실측:

```
PATCH /notices/2  {"pinned":false}
  → 200, title·content·banner 그대로
```

⚠️ **예약·만료 시각을 지우는 것은 PATCH 로 안 된다** — `null` 이 "그대로" 라서다.
지울 때는 `PUT` 을 쓴다. `updateNotice()` 를 그 용도로 남겨뒀다.

## 13-2. 공지 열람 수가 없다 ✅ 반영됨 (2026-09-07)

`readCount` 가 들어왔다. '열람' 컬럼을 `<Unfilled/>` 에서 실값으로 바꿨다.

목업은 `281/296` 형태의 진행률이었는데 서버가 주는 건 **읽은 사람 수 하나**다.
분모(대상 인원)는 범위마다 달라(전체/지점/반/개별) 목록 응답에 없다 — `N명` 으로 표시한다.

## 13-3. (확인만) 발송 경로가 범위별로 갈린다

하나의 POST 에 `scope` 를 넘기는 방식이 아니다.

| 범위 | 경로 |
|---|---|
| 전체 | `POST /notices/all` |
| 지점 | `POST /notices/branches/{academyId}` |
| 반 | `POST /notices/classes/{classId}` |
| 개별 | `POST /notices/students/{enrollmentId}` |

권한이 경로 단위로 걸려 있어서다(전체는 본사, 반은 담임). 화면은 범위 선택에 따라
경로를 바꿔 부르고, **전 지점 권한이 아닌 계정에는 '전체' 옵션을 아예 안 보여준다.**

## 13-4. 행정 요청 수신함·1:1 채팅은 그대로 목업이다

- **행정 요청** — 대응 API가 없다. I-3(앱 행정 요청 항목 리스트) 미확정 항목이다
- **1:1 채팅** — E-6(외부 메신저 선정) 대기. 선정 전까지 착수 불가로 표시돼 있다

# 14부. 질의응답 (2026-09-04)

## 14-1. 슬롯 조회가 날짜 하나씩이라 주간 표를 그리려면 5번 부른다 ✅ 반영됨 (2026-09-07)

`from`·`to` 가 들어왔다(양끝 포함). 주간 표가 5회 → 1회다.
5개 중 하나만 늦어도 표가 어긋난 채 그려지던 것도 같이 없어졌다. 실측:

```
?academyId=8&from=2026-09-01&to=2026-09-07  → 4건
날짜별 7회 합                                → 4건 (id 집합 동일)
```

`date` 도 그대로 남아 있다 — 일간 화면이 생기면 쓴다.

## 14-2. 예약자 응답에 반·과목이 없다 — 반은 반영됨, 과목은 남음

- **반 ✅ (2026-09-07)** — `className` 이 들어왔다. 컬럼을 실값으로 바꿨다.
  다만 시드에 예약 데이터가 없어 **스펙으로만 확인**했다. 예약이 생기면 실측한다
- **과목 ❌** — 예약 자체에 과목 항목이 없다. 신청 폼에 과목 선택이 있는지부터
  확인이 필요하다. 그때까지 `<Unfilled/>` 로 둔다

## 14-3. 문제 사진 첨부가 없다

목업은 신청 시 **문제 사진**을 올리는 흐름이다(통계 칸에 "문제 사진 포함 N건",
그리드 셀에도 첨부 아이콘). 예약 응답에 관련 필드가 없다.

> 앱에서 사진을 받고 있다면 개수·URL을 실어주면 된다. 안 받고 있다면 목업 쪽을 접어야 한다.

## 14-4. 온라인 질의응답은 도메인이 없다

목업은 대면/온라인 두 유형을 두고 **온라인은 노출만 꺼둔 상태**로 설계했다
("나중에 스위치만 켜면 된다").

서버에는 `qna/offline` 만 있다. 온라인을 열 때 같은 모델을 재사용할지,
별도로 만들지 확인이 필요하다.

## 14-5. (확인만) `closed` 와 `full` 은 다른 축이다

둘 다 앱에서는 "마감"으로 보이지만 원인이 다르다 —
`closed` 는 운영자가 닫은 것, `full` 은 정원이 찬 것이다.
관리자 화면에서는 구분해서 표시하고, `closed` 는 눌러서 되돌릴 수 있게 했다.

# 15부. 문자 발송 (2026-09-07)

화면 F-4.4. **탭 3개 중 '템플릿 관리' 하나만 연동됐다.**

## 15-1. 발송 자체가 없다 ★

`/notification-templates` 는 **템플릿 관리만** 한다. 사람이 대상을 골라 지금 보내는
경로가 없다. 서버 알림은 전부 **이벤트 트리거**(등원·승인·상담 11종)로 나간다.

목업의 '메시지 발송' 탭은 반·학년 등 범위를 골라 보내는 화면이다. 대응 API가 없어
목업으로 두고 "예시입니다" 안내를 띄웠다.

> 확인 필요: 수동 발송이 요구사항에 있는지부터. 없다면 목업 쪽을 접어야 한다.
> 있다면 대상 선택 + 발송 API가 필요하다.

## 15-2. 발송 이력이 없다 ★

보낸 기록을 조회할 경로가 없다. 목업 '발송 이력' 탭(발송시각·템플릿·채널·대상수·성공수)이
통째로 빈다.

자동발송이 주 경로인 만큼 **"어제 미등원 알림이 몇 명에게 나갔나"** 를 못 본다.
알림톡은 건당 과금이라 정산 근거로도 필요하다.

> 요청: 발송 로그 조회. 최소한 (발송시각, 템플릿, 채널, 대상 수, 성공 수).

## 15-3. 알림톡인데 심사를 안 타는 템플릿이 발송 가능해진다 ★

`reviewStatus=NOT_REQUIRED` 인 **카카오 알림톡** 템플릿이 둘 있다
(`APPROVAL_HANDED_OVER`, `APPROVAL_REMINDER`). 이 둘은 문구만 확정하면
**카카오 심사 없이 `sendable=true`** 가 된다.

```
PATCH /notification-templates/10/content
  {"titleTemplate":"위임","bodyTemplate":"[D.Lab] {studentName} …","contentConfirmed":true}
→ 200  channel=KAKAO_ALIMTALK  reviewStatus=NOT_REQUIRED  sendable=true
```

카카오는 사전 승인된 문안만 허용하므로, 이 상태로 실제 발송하면 **화면은 "나감"인데
카카오에서 거부**된다. 원인이 우리 쪽에 안 남는다.

> 확인 필요: 시드 값이 잘못된 것인지, `NOT_REQUIRED` 를 알림톡에도 허용하는 설계인지.
> 후자라면 `sendable` 판정에 "알림톡이면 APPROVED 여야 한다"가 빠져 있다.

## 15-4. 문구 수정에는 학생명 변수 검사가 없다

등록(`POST`)은 학생명 변수가 없으면 거부한다고 문서에 적혀 있다. 그런데
수정(`PATCH .../content`)은 통과한다 — 등록 때 넣은 변수를 **수정으로 빼버릴 수 있다.**

```
PATCH .../content {"titleTemplate":"승인요청","bodyTemplate":"[D.Lab] 승인 요청이 도착했습니다.",
                   "requiredVariables":"resolvedAt"}
→ 200
```

다자녀 학부모가 "이거 누구 얘기지" 하는 걸 막자고 넣은 검사인데, 수정 경로로 우회된다.

> 요청: `PATCH` 에도 같은 검사를 걸 것.

## 15-5. 템플릿 수정 시각·수정자가 없다

목업 표의 '최종 수정'·'수정자' 컬럼에 대응하는 값이 없다. `reviewedAt` 은 심사 시각이라
문구를 언제 누가 고쳤는지와 다르다. `<Unfilled/>` 로 뒀다.

## 15-6. 템플릿명이 없다

응답에 `event` 코드만 있고 사람이 읽을 이름이 없다. 화면이 11개 이벤트의 한글 이름을
갖고 있다(`EVENT_LABEL`). **이름이 프론트에 박혀 있어 이벤트가 늘면 화면도 고쳐야 한다.**

> 요청: `displayName` 을 함께 싣거나, 이벤트 목록 조회를 열어줄 것. 우선순위 낮음.

## 15-7. (확인만) 템플릿은 이벤트당 하나다

같은 이벤트로 또 등록하면 409 (`이 이벤트의 템플릿이 이미 있습니다`). 11개 이벤트가
이미 다 차 있어 **'템플릿 등록' 버튼은 지금 누를 자리가 없다** — 목업 버튼은 두되
이유를 붙여 비활성화했다. 삭제 API도 없다.

## 15-8. (확인만) 발송 여부는 세 축이 모두 통과해야 한다

`active` · `contentConfirmed` · `reviewStatus` 셋이 다 통과해야 나간다. 서버가
`sendable` 하나로 합쳐 주므로 화면은 그 값을 쓴다. 심사 배지만 보면 "승인인데 왜
안 나가지"가 된다.

승인된 알림톡 문구를 고치면 심사가 `DRAFT` 로 되돌아가는 것도 실측으로 확인했다.

# 16부. 연간 행사 (2026-09-07)

화면 F-4.11-10. 붙인 것은 `/holidays` 다. **이름 그대로 '휴일' 마스터이지
'연간 행사' 마스터가 아니다.**

## 16-1. 행사 유형 다섯 중 하나만 서버에 있다 ★

| 목업 유형 | 서버 |
|---|---|
| 휴원 | ✅ `PUBLIC` · `SUBSTITUTE` · `TEMPORARY` · `ACADEMY` |
| 모의고사 | ❌ |
| 특강 | ❌ (`/lectures` 는 강좌 마스터라 일정 축이 다르다) |
| 설명회 | ❌ |
| 행사 | ❌ |

화면 목적이 **"관리자가 등록한 날은 학생이 학습계획을 못 세운다"** 인데, 그 차단
스위치(`planExcluded`)는 휴일에만 달려 있다. 모의고사 당일도 계획을 막아야 하는데
(목업 13건 중 6건이 모의고사) 넣을 곳이 없다.

지금 대응: 등록 폼에서 휴일 4종만 고르게 하고, 화면에 이유를 띄웠다.

> 요청: 일정 종류를 넓히거나(휴일 `type` 에 `EXAM` 등 추가), 별도 일정 도메인.
> **어느 쪽이든 `planExcluded` 가 붙어 있어야 한다** — 그게 이 화면의 존재 이유다.

## 16-2. 하루짜리다 — 연휴가 여러 행이 된다

`date` 하나뿐이라 기간(from~to)이 없다. 목업의 기간 입력은 **하루씩 쪼개 N번 POST**
하는데, 중간에 실패하면 앞쪽 날짜만 등록된 채로 남는다. 건별 성공/실패를 화면에 적었다.

같은 날짜에 두 번 넣으면 409 (`이미 등록된 날짜입니다`)라, 실패한 뒤 다시 시도하면
성공한 앞쪽에서 409 가 난다.

> 요청: `from`·`to` 를 받는 등록. 우선순위 중간.

## 16-3. 본사가 지점 휴일을 못 본다 ★

```
지점 계정 조회 → 전 지점 공통 1건 + 자기 지점 1건
본사 계정 조회 → 전 지점 공통 1건만
본사 + academyId=8 → 여전히 1건 (파라미터가 무시된다)
```

본사는 **"분당이 7/15 쉰다"를 모른다.** 다른 목록은 본사가 전 지점을 보는데
여기만 반대다. 연간 행사표는 본사가 전 지점 일정을 훑는 화면이라 뒤집혀 있다.

> 요청: 본사 조회에 지점 휴일 포함, 또는 `academyId` 를 실제로 적용할 것.

## 16-4. 대상·비고가 없다

목업의 '대상'(전체/신청자/외부)과 '비고'가 응답에 없다. 대상 자리에는 지점 범위
(전 지점/지점)를 넣었고 — 축이 다르지만 사용자가 판단에 쓰는 값이라 — 비고는
`<Unfilled/>` 로 뒀다.

## 16-5. 전년도 복사가 없다

목업의 '전년도 복사' 버튼에 대응하는 경로가 없다. 공휴일은 해마다 날짜가 바뀌어
그대로 복사하면 틀리지만, 학원 자체 일정은 되풀이되는 것이 많다. 지금은 비활성화했다.

> 우선순위 낮음. 다만 시즌 시작마다 수십 건을 손으로 넣게 된다.

## 16-6. (확인만) 전 지점 공통은 본사만 넣는다

```
지점 계정으로 전 지점 공통 등록 → 403 "전 지점 공휴일은 본사만 등록할 수 있습니다."
```

지점 관리자가 넣으면 다른 지점 급식까지 막혀서다. 화면은 지점 계정에서
'전 지점 공통' 선택지를 비활성화한다.

## 16-7. (확인만) 급식 가능일용이지 교습비 일수가 아니다

백엔드 주석에 명시돼 있다 — 학원은 삼일절·어린이날에도 운영한다.
수납 화면에서 이 데이터를 일수 계산에 쓰면 안 된다.

# 17부. 앱 운영 · 사용자 관리 (2026-09-07)

## 17-1. 푸시 발송·발송 이력이 없다 ★ (F-C-6)

푸시를 사람이 골라 보내는 경로도, 보낸 기록을 조회하는 경로도 없다.
목업 '푸시 발송' 탭(발송시각·제목·대상·수신·개봉률·상태)이 통째로 빈다.

화면 주석에 적힌 전제 — **푸시·알림톡 로그를 `notification_logs` 한 테이블에 채널
컬럼으로 적재** — 도 아직 서버에 없다. 채널별로 나누면 "이 학생에게 언제 무엇이
갔나"를 한 번에 못 본다. 알림톡 발송 이력(15-2)과 **같은 요청이다.**

> 요청: 발송 로그 조회. 최소 (발송시각, 채널, 템플릿/제목, 대상 수, 성공 수).

## 17-2. 배너에 노출 위치·클릭 수가 없다

배너는 별도 도메인이 아니라 **공지의 `banner` 축**이다. 그래서 목록 자체는 붙였는데
목업의 '노출 위치'(홈 상단/홈 팝업/마이페이지)와 '클릭 수'가 없다.

- 노출 위치 → 가장 가까운 값이 `pinned`(상단 고정)라 그걸 넣었다. **축이 다르다**
- 클릭 수 → `<Unfilled/>`. 공지 `readCount`(열람 수)는 있어 그건 함께 보여준다

> 확인 필요: 배너 노출 위치를 운영에서 실제로 나누는지. 나눈다면 공지에 축을 더해야 한다.

## 17-3. 동의율·가입자 수 집계가 없다

`/app-config/terms/agreements/{accountId}` 는 **계정 하나**의 동의 현황이다.
목업 상단의 '앱 가입 289명 / 재원 296명', 약관별 '동의율 %'을 낼 경로가 없다.
전 계정을 돌며 세는 건 화면이 할 일이 아니다.

> 요청: 약관별 동의 수, 앱 가입 계정 수.

`TermsStatus.agreed` 가 `null` 이면 **아직 응답한 적이 없다**는 점은 잘 설계돼 있다 —
'동의 안 함'과 섞이면 가입 흐름에서 다시 물어볼지를 판단하지 못한다.

## 17-4. 버전별 사용자 분포·스토어 심사일이 없다

목업 '최신 버전 적용률'(막대)과 '심사 통과' 날짜에 대응하는 값이 없다.
버전 게이트를 올릴지 판단하는 근거가 적용률인데 그게 없다. `<Unfilled/>` 로 뒀다.

> 우선순위 중간. 적용률 없이 최소 지원 버전을 올리면 얼마나 잘려 나가는지 모른 채 올린다.

## 17-5. (확인만) 점검 모드는 목업에 없던 축이다

`GET /app-config` 에 `maintenance` 가 있다. **켜면 그 플랫폼 전 사용자가 앱을 못 쓴다.**
목업에는 이 개념이 없었는데, 켜져 있는데 화면 어디에도 안 보이면 "왜 앱이 안 되지"를
못 짚는다. 그래서 상단 경고와 버전 카드 배지로 드러내고, 켤 때는 확인을 받는다.

```
PUT /app-config/ANDROID/maintenance {"maintenance":true,"message":"점검 중"} → 200
```

## 17-6. (확인만) 약관은 고치지 않고 버전을 올린다

수정 API가 없는 것이 실수가 아니다 — 덮어쓰면 이미 동의한 사람들의 근거가 사라진다.
개정은 `POST` 로 새 버전을 등록하는 것이다. 화면의 '새 버전 배포'는 본문 입력이
필요해 별도 화면이 있어야 한다. 지금은 비활성화했다.

## 17-7. ✅ 해결됨 — 사용자 관리, 읽는 경로가 생겼다 (F-4.10-2)

`GET /staff/accounts` 신설. `accountId`·`roles`·`status`·`lastLoginAt` 이 다 온다.

```
GET /staff/accounts?academyId=8
→ 200 [{"accountId":2,"loginId":"branch","accountType":"EMPLOYEE","status":"ACTIVE",
        "roles":["BRANCH_ADMIN"],"name":"분당관리자","deptName":"운영팀",
        "positionName":"팀장","academyId":8,"academyName":"분당",
        "locked":false,"mustChangePassword":false,"lastLoginAt":"2026-09-07T04:02:54Z"}, …]
```

역할 변경(`PUT .../roles`)의 대상 `accountId` 를 여기서 얻는다. 승인·탈퇴·이력 경로도 함께 열렸다.

| 있는 것 | 없는 것 |
|---|---|
| `PUT /staff/accounts/{accountId}/roles` (역할 재설정) | **계정 목록 조회** |

실측:

```

→ {"kind":"EMPLOYEE","id":1,"academyId":8,"name":"통합관리자",

```

**역할을 바꾸는 API는 있는데 지금 역할이 뭔지 볼 수가 없고, `accountId` 가 응답에

이름·연락처뿐이라 **붙이지 않고 목업으로 뒀다** — 반쯤 채우면 "권한 관리가 된다"고
오해된다.

> 요청 (하나만 되면 화면이 열린다):
> 1. `StaffResponse` 에 `accountId`·`roles`·`loginId` 를 싣거나
> 2. 계정 목록 조회(`GET /staff/accounts`)를 열어줄 것
>
> Phase 0 주의사항이 **"RBAC는 이 Phase에서 완성 필수"** 다. 권한 화면 없이
> 개인정보 노출 메뉴가 열리는 것이 리스크#5 로 적혀 있다.

## 17-8. (참고) 키오스크·장비 설정이 생겼다

`POST /branch-configs/{academyId}/kiosk-credential`,
`PATCH /branch-configs/{academyId}/nebula-device-id`.

기초 관리(F-4.10-1)나 지점 설정 쪽에 붙을 것들이다. 둘 다 **되돌릴 수 없는 조작**이라
화면에 경고가 필요하다 — 자격증명을 재발급하면 그 지점 키오스크가 즉시 인증에
실패하고(키오스크 백엔드 `stores` 값을 같이 바꿔야 복구), 장비 ID를 틀리게 넣으면
방화벽 해제가 다른 지점 와이파이를 향한다.

# 18부. 청구 기준 · 기초 관리 · 학원생 현황 (2026-09-07)

## 18-1. 청구 기준의 축이 화면과 다르다 ★ (F-4.10-5)

| 목업 | 서버 |
|---|---|
| 항목별 — 교습비·특강비·**등록비**·**급식비** | **(학년 × 좌석유형)** 정가만 |
| 결제 채널 (가상계좌/PG·VAN/대성전산/급식업체 PG) | 없음 |

| 청구 기수 (1기·3기) | 없음 |
| 사용 여부 | 없음 |

교습비만 축이 맞고 나머지는 둘 곳이 없다. 등록비 결제주체(D-9)가 최우선 미확정
항목인데, 그걸 담을 자리 자체가 아직 없다.

> 요청: 청구 항목 마스터. 최소 (항목 종류, 금액, 결제 채널, 납기, 사용 여부).

## 18-2. 월별 교습일수가 비어 있으면 청구가 계산되지 않는다 ★

`GET /tuition/months` 가 비어 있는데(시드 기준 0건) **그 사실이 어디에도 안 보였다.**
청구 시점에야 알게 된다. 화면 상단에 미입력 월을 붉게 드러내고 한 달씩 채우게 했다.

실측에서 확인한 두 가지:

- **PUT 본문이 배열이 아니라 단건이다.** 배열로 보내면
  `요청 본문 형식이 올바르지 않습니다`(400) — 스펙만 보면 배열로 오해하기 쉽다
- **요청과 응답의 `month` 모양이 다르다.** 보낼 때 `"2026-09"`, 받을 때 `9`(정수) + `year`

```
PUT /tuition/months {"academyId":8,"month":"2026-02","teachingDays":30}
  → 400 "2월은 28일까지입니다."
PUT /tuition/months {"academyId":8,"month":"2026-02","teachingDays":27}
  → 200 {"id":14,"year":2026,"month":2,"teachingDays":27}
```

달력을 **상한으로만** 확인하는 설계가 맞다 — 교습일수는 달력 일수가 아니다.
화면이 규칙을 추측해 자동 산출하지 않게 주석에 적었다.

## 18-3. ✅ 해결됨 — 환불 기준 (F-4.10-5)

목업 '환불 기준' 탭(개강 전 100% · 1/3 경과 전 2/3 …)에 대응하는 경로가 없다.
학원법 시행령 기준이라 값 자체는 정해져 있는데 저장할 곳이 없다.
`GET /billing-standards/refund-rules` 신설. **서버가 학원법 반환기준을 값으로 들고 있다** —
시드와 무관하게 계정을 가리지 않고 나온다. `note` 에 "할인을 받았으면 환불액이 음수가 될 수
있다" 같은 주의까지 들어 있어 그대로 화면에 쓴다.

## 18-4. 기초 마스터에 코드·비고·사용여부가 없다 (F-4.10-1)

7종을 붙였는데 **목업 표의 세 컬럼이 어느 마스터에도 없다.**

- **코드** — 목업은 `TR-NA`·`DEP-ME` 같은 값을 쓴다. 운영 중 이름이 바뀌어도 참조가
  안 깨지게 하는 값인데 서버에는 이름뿐이다
- **비고** — 설명 문구
- **사용여부** — 지금은 지우는 것 말고 끄는 수단이 없다. 과거 데이터가 참조하는
  마스터를 지우면 그 참조가 깨진다

> 요청: 세 필드. 특히 **사용여부**는 삭제 대신 쓸 수단이 없어 실제로 곤란하다.

## 18-5. 마스터마다 되는 조작이 다르다 (확인만)

| 마스터 | 조회 | 등록 | 수정 | 삭제 |

## 18-6. (확인만) 전년도 복사가 표별 건수를 돌려준다

```
POST /masters/yearly-copy {"academyId":8,"fromYear":2026,"toYear":2027}
→ 200 {"fromYear":2026,"toYear":2027,
       "copied":{"department":1,"period":34,"courseType":1,"class":4,
                 "curriculum":0,"approvalItem":3,"penaltyItem":8,"tuition":1,…}}
다시 →  409 "2027년에 이미 기초 데이터가 있습니다. 비운 뒤 다시 시도하세요."

"완료"뿐이면 잘못 눌렀을 때 뭘 확인해야 할지 모른다.

## 18-7. 학원생 현황은 집계 축이 다르다 ★ (F-C-2)

`GET /statistics` 는 **대시보드 요약 하나**다. 화면이 요구하는 것은 반별·계열별·
재수구분별 **집계 표**다.

서버가 주는 것:

```
students{enrolled,total,byStatus} · attendance{confirmedDays,attendanceRate,byStatus}
studyTime{totalMinutes,avgMinutesPerDay,ranking[10]} · penalty{merit,demerit,count}
meals{appliedTotal} · revenue{billed,received,unpaid,byType}
```

화면이 필요한 것: `groupBy=class|track|month` 별 인원·정원·충원율·증감.

**클라이언트 집계로 대신하지 않았다.** 화면 주석이 그걸 금지하고 있다 —
전 원생을 내려받아 프론트에서 세면 원생 수가 늘수록 그대로 느려진다.

> 요청: `GET /students/stats?groupBy=class|track|month`.
> 화면 주석에 이미 그 형태로 적혀 있다.

`/statistics` 자체는 쓸 데가 있다 — 다만 이 화면이 아니라 대시보드다.

# 19부. 특강 기초 설정 (2026-09-07)

화면 F-4.10-4. `/lectures` 를 붙였다. **F-4.7(특강 관리)과 같은 엔드포인트를 쓰되
역할이 다르다** — 여기는 종류별 목록과 접수·노출 여닫기, F-4.7 은 개설·명단·회차·출석부.

## 19-1. 특강 유형 마스터가 없다 ★

목업은 이 화면을 **마스터**로 본다 — 특강 유형·설명회 신청 항목·기본 정원/특강비
템플릿을 관리하고, 개설할 때 그 선택지를 고른다는 구조다.

서버에는 그런 마스터가 없다. 종류는 `lectureType` enum **두 개뿐**이다.

```
LectureCreate.lectureType : ["LECTURE", "BRIEFING"]
```

목업이 쓰는 **단과·실전·해설** 구분은 넣을 곳이 없다. 기본 정원·특강비 템플릿도 없어
특강마다 매번 처음부터 채워야 한다.

지금 대응: 화면을 "개설된 특강·설명회를 종류별로 보고 접수·노출을 여닫는" 것으로
좁히고, 세부 구분이 없다는 것을 화면에 밝혔다.

> 요청 (둘 중 하나):
> 1. `lectureType` 에 값을 더하거나 (단과·실전·해설)
> 2. 특강 유형 마스터를 신설하고 `lecture.categoryId` 로 참조
>
> 2번이면 기본 정원·특강비도 함께 담을 수 있다. **우선순위 중간** —
> 지금도 개설·운영은 되고, 분류가 안 될 뿐이다.

## 19-2. 특강 코드 — 필드는 있고 값이 없다 (정정)

처음에 "응답에 없다"고 적었는데 **틀렸다.** `LectureDetail` 에 `code` 가 있고 응답에도 온다.
다만 시드 4건이 전부 `null` 이라 화면에서 비어 보였던 것이다. 목업의 `LEC-2606-01` 형식으로
채번하는 규칙이 있는지는 아직 모른다.

> 요청: 채번 규칙 확인. 등록 시 서버가 매기는지, 화면이 입력받는지.

## 19-3. 특강 삭제가 없다

`DELETE /lectures/{id}` 가 없다. 잘못 만든 특강을 지울 수 없어 `DRAFT` + 숨김으로
두는 수밖에 없다. 목업의 '삭제' 버튼에 대응하는 것이 없다.

신청이 붙은 특강을 지우면 안 되는 건 맞다. 다만 **신청 0건인 초안은 지울 수 있어야 한다.**

> 요청: 신청이 없는 `DRAFT` 특강에 한해 삭제.

## 19-4. (확인만) 접수 상태와 앱 노출은 별개 축이다 ★

```
PUT /lectures/{id}/status   {"status":"OPEN"}    ← 지금 받는가
PUT /lectures/{id}/visible  {"visible":true}     ← 앱에 보이는가
```

**접수를 열어도 노출을 안 켜면 앱에 안 보인다.** 시드의 특강 3건이 전부
`visible=false` 였고, 그중 2건은 `status=OPEN` 이었다 — 받는다고 해놓고 안 보이는 상태다.
"왜 신청이 안 들어오지"의 흔한 원인이라 화면 상단에 그 조합을 따로 경고한다.

0803 회신의 "개설 시에만 노출"이 이 축이다.

## 19-5. (확인만) 등록은 이름과 종류만 받는다

```
POST /lectures {"academyId":8,"year":2026,"lectureType":"LECTURE","name":"…"}
→ 200 status=DRAFT visible=false capacity=null fee=0 …
```

정원·기간·비용·담당은 `PATCH` 로 따로 채운다. **회차는 또 따로 추가한다** —
회차 없는 특강은 출석부를 못 만들고 신청도 받을 수 없다(F-4.7 주석).
그래서 이 화면의 등록 버튼 옆에 "정원·기간·비용·회차는 특강 관리에서 채우세요"를 적었다.

# 20부. 특강 담당 강사 — 필드명을 바꾸면 조용히 깨진다 ★ (2026-09-07 오후)

특강 목록의 '담당'이 전부 **'미지정'** 으로 보인다. 필드명이 틀린 것으로 오해하기 쉬운데
**시드 4건의 `teacherName` 이 전부 `null`** 이기 때문이다.

```
GET /lectures?academyId=8&year=2026
→ 필드: applyFrom applyTo capacity code confirmedCount description endDate fee id
        lectureType name startDate status teacherId teacherName visible waitlistedCount
→ 4건 모두 teacherId=null, teacherName=null
```

`/v3/api-docs` 의 `LectureDetail` 도 같다. **`instructorName` 이라는 이름은 응답에도
스펙에도 없다.** 한 번 그 이름으로 바꿨다가 되돌렸는데, 인터페이스까지 같이 바꾸면
`tsc` 가 통과해서 **화면만 영구히 '미지정'** 이 된다 — 담당을 넣어도 안 보인다.

> 요청: 시드 특강에 담당 강사를 넣어 달라. 지금은 이 컬럼이 비어 있는지 깨진 건지
> 화면만 봐서는 구분할 수 없다.

# 21부. 직원 계정 등록 (F-4.10-2) — 2026-09-08

목업의 '계정 등록' 버튼에 폼을 붙이면서 실호출로 확인한 것들이다.
계정 생성 자체는 된다. **`POST /staff/employees` 하나가 사람과 계정을 함께 만든다** —
신규 접수 등록(POST→PATCH)과 달리 부분 성공이 없다.

```
POST /staff/employees
{"academyId":8,"loginId":"qa_test_1","name":"QA테스트","password":"…","roles":["STAFF"]}
→ 200
```

## 21-1. 만든 뒤 인적사항을 고칠 수 없다 ★

```
PUT    /staff/employees/3 → 404
PATCH  /staff/employees/3 → 404
DELETE /staff/employees/3 → 404
```

`/staff/teachers/{id}` 도 같다. **이름·부서·직급·연락처·이메일은 저장하는 순간 고정된다.**
바꿀 수 있는 것은 역할(`PUT .../roles`)과 상태(`approve`·`withdraw`)뿐이다.

오타 하나에 탈퇴 처리하고 새로 만드는 수밖에 없어서 **`WITHDRAWN` 계정이 목록에 쌓인다.**
(확인용으로 만든 3건이 지금 그렇게 남아 있다.) 화면에는 저장 전에 그 사실을 적어 뒀다.

> 요청: `PUT`·`PATCH /staff/employees/{id}`·`/staff/teachers/{id}`.

## 21-2. 아이디 중복 확인 경로가 없다

사전 확인 API가 없어 목업의 '중복확인' 버튼을 만들 수 없다. 저장을 눌러야 알 수 있다.

```
POST /staff/employees  (같은 loginId 재사용)
→ 400 {"code":"INVALID_REQUEST","message":"이미 사용 중인 로그인 아이디입니다."}
```

메시지가 명확해서 그대로 아이디 칸 옆에 띄웠다. 다만 **폼을 다 채운 뒤에 실패한다.**

> 요청: `GET /staff/accounts/login-id-available?loginId=` 같은 확인 경로.

## 21-3. 첫 로그인 비밀번호 변경을 강제할 수 없다 ★

생성 요청에 `mustChangePassword` 가 없다. 만들어진 계정은 `mustChangePassword: false` 다.
**관리자가 정해준 비밀번호를 그 사람이 계속 쓰고, 관리자는 그 비밀번호를 안다.**

우회로는 있다 — `POST /app-accounts/{accountId}/temporary-password` 가 **직원 계정에도 먹는다**
(스펙에는 앱 계정(F-4.12-1)으로 분류돼 있는데 실제로 200이다).

```
POST /app-accounts/3/temporary-password → 200 {"temporaryPassword":"wPLSw2fuW5"}
```

> 요청: 생성 요청에 `mustChangePassword` 를 받거나, 관리자가 만든 계정은 기본 `true` 로.

## 21-4. 응답이 만들어진 계정을 안 돌려준다

```
→ 200 {"kind":"EMPLOYEE","id":3,"academyId":8,"name":"QA테스트",
       "accountId":null,"loginId":null,"roles":[], …}
```

계정은 분명히 만들어졌는데(같은 `loginId` 재요청이 중복으로 막힌다) **`accountId`·`loginId` 가
null, `roles` 가 빈 배열**로 온다. 응답으로 행을 그리면 빈 줄이 생겨서, 저장 후 목록을 다시 부른다.

> 요청: 생성 응답에 `accountId`·`loginId`·`roles`·`status` 를 채워 달라.

## 21-5. (확인만) 누가 만들었느냐로 즉시 사용 여부가 갈린다 ★

| 만든 계정 | 결과 |
|---|---|
| `admin` (SUPER_ADMIN) | `ACTIVE` — 바로 로그인된다(실제 200 확인) |
| `branch` (BRANCH_ADMIN) | `PENDING` — 로그인하면 `SIGNUP_PENDING` "가입 승인 대기 중입니다" |

**역할이 아니라 만든 사람으로 갈린다.** 지점 관리자가 `STAFF` 를 만들어도 `PENDING` 이다.
지점 담당자에게 이걸 안 알리면 계정을 만들어 주고 "왜 로그인이 안 되냐" 를 듣게 되므로
폼에 적어 뒀다.

## 21-6. 지점 관리자가 `SUPER_ADMIN` 을 요청할 수 있다 ⚠

지점(`branch`) 계정으로 전 지점 권한을 달아 만드는 것이 **막히지 않는다.**

```
POST /staff/employees  (branch 토큰)
{"academyId":8,"loginId":"qa_esc","roles":["SUPER_ADMIN"], …} → 200, status=PENDING
```

다른 지점에 만드는 것은 서버가 막는다(`OTHER_BRANCH_ACCESS_DENIED`). **역할만 안 막는다.**
`PENDING` 이라 본사 승인 전에는 못 쓰지만, 승인 화면에서 요청된 역할을 못 보고 눌러주면
전 지점 권한이 넘어간다. 화면에서는 자기 권한 위를 못 고르게 막았다.

> 요청: 서버에서도 **자기 역할보다 높은 역할의 생성·요청을 거부**해 달라.
> 그리고 승인 목록에 **요청된 역할**이 보여야 한다.
