### 1-1 특강 상세 모달 — 가장 먼저

들어갈 입구만 만들면 막혀 있던 수정·삭제·차수·출석부가 한꺼번에 열린다.

```
PATCH  /lectures/{id}                    수정      ← 호출 코드 있음, 진입점 없음
PUT    /lectures/{id}/status             상태
PUT    /lectures/{id}/visible            노출
POST   /lectures/{id}/sessions           차수 추가
GET    /lectures/{id}/attendance-targets 출석 대상
GET/PUT /lectures/sessions/{id}/attendances  차수별 출결
```

**단건 조회 API 는 필요 없다**(2026-09-14 확인). `GET /lectures` 목록 응답이 상세를 다 내려준다 —
설명·정원·금액·기간·신청기간·담당교사·분류·확정/대기 인원까지. **모달은 목록에서 받은 값으로 채운다.**

### 1-7 상벌점 — 서버는 다 있다

```
GET/POST/PUT/DELETE /penalty-items        항목      ?year= 필수
GET/POST/PUT/DELETE /penalty-rules        자동 부여 규칙 (+ /{id}/active 토글)
POST   /penalties                         수동 부여
DELETE /penalties/{id}                    취소
```

**"자동 부여분을 사람이 조정"은 서버로 이미 된다.** 화면만 없다.

### 1-2 수납 청구 생성

```
POST /tuition/billings/monthly     월 청구
POST /tuition/billings/admission   입학금
POST /billings                     청구 생성
POST /billings/{id}/payments       수납 처리
DELETE /billings/{id}              청구 취소
DELETE /billings/payments/{id}     수납 취소
```

⚠ **청구를 자동 생성할지 직원이 만들지가 클라이언트 회신 대기 중이다.**
어느 쪽이든 위 API 는 붙어야 하므로 **직원이 만드는 쪽부터** 붙이고 자동 생성은 나중에 얹는다.

✅ **09-14 직원 생성분 완료.** 수납현황(F-4.8) 통합 매출장에 붙였다.
청구 등록(교습비 월 / 그 밖) · 수납 · 청구 취소. 회신이 오면 여기에 자동 발행을 얹는다.
`POST /tuition/billings/admission`(입학금)은 아직 안 붙였다 — 신규 접수 등록 흐름에
들어가야 자연스러운데 그건 1-3 과 묶여 있다.

#### 2-1 은 구역만 만들면 안 된다

구역을 만들면 `seatCount: 0` 이라 배치도가 빈 채로 남는다. 등록 폼에서 행·열을 함께 받아
두 호출을 이어 준다 — `grid` 가 그래서 있다.

```

   → POST /seats/areas          구역 생성
   → POST /seats/masters/grid   좌석 40개 자동 생성
```

- 좌석에는 **x·y 좌표**가 필요하다. 배치도를 그리는 근거이고 없으면 화면이 빈다
- 고장·공사로 못 쓰는 자리는 삭제가 아니라 **`PATCH /seats/{id}/usable` 로 사용중지**한다.
  지우면 배치도에 구멍이 생긴다

#### 3-1 계정별 메뉴 노출 — 서버 계약 (2026-09-16 회신)

```
GET /admin/menus              카탈로그(트리). 설정 화면의 체크박스
GET /admin/menus/mine         내 계정이 볼 수 있는 코드. 좌측 메뉴를 이걸로 그린다
PUT /admin/staff/accounts/{id}/menus   { menuCodes: [...] } — 통째로 교체
```

- **빈 배열이면 제한 해제.** 설정이 없는 계정에는 전체가 내려온다
- **부모 코드를 줘도 자식은 안 열린다.** 각 코드가 독립이다 — `billing` 만 주면
  `tuition`·`scholarship` 등은 막힌다. 설정 화면이 부모를 체크할 때 자식까지 함께
  실어 보낸다(`parentCode` 로 묶는다). 서버가 자동 포함하면 "수납현황만 보여주려 했는데
  청구기준 편집까지 열리는" 것을 막을 수 없어서다
- **한 화면이 여러 코드의 API 를 부르면 그 코드를 전부 줘야 한다.** 수납현황에서
  현금영수증을 발급하면 `billing` 만으로는 403 이다
- `enforceable: false` 인 셋(대기자·시간표·신상기록부)은 **화면에서만** 걸린다.
  서버 API 가 없어 막을 경로가 없다

매핑은 `src/data/menuCodes.ts` 에 있다. **코드를 화면 id 로 맞추지 않는다** — 서버는
업무 영역(권한 도메인), 화면은 메뉴 항목이라 단위가 다르다.
어긋나면 `npm run check:frow` 가 잡는다.

#### 3-3 자주 쓰는 메뉴 (2026-09-16)

```
GET/PUT /admin/menus/favorites   { menuCodes: [...] } — 통째 교체, 최대 8개
```

노출 설정(3-1)과 **다른 개념이다.** 저건 최고관리자가 정하는 권한이고 이건 본인이 고르는
편의다. 볼 수 없는 메뉴는 서버가 안 담는다.

**★ 화면이 아니라 업무 영역(코드) 단위다.** 서버가 코드로 저장해서다 — 그래서
'학생 검색' 과 '신규 접수 등록' 을 따로 담을 수 없고 **'학생 관리' 하나**가 된다.
코드 하나가 화면 여럿을 덮는 6개(`student`·`attendance`·`seat`·`staff`·`statistics`·`lecture`)는
**대표 화면을 `menuCodes.ts` 의 `CODE_MAIN_SCREEN` 에 적어 뒀다** — 목록 순서에 맡기면
매핑을 손댈 때 링크가 조용히 바뀐다.

기존 기본 목록(학생 검색·출결 현황·사유 승인·상담일지·알림 발송·수납현황)은 화면 단위라
사용자가 고를 수 있는 것보다 촘촘하다. **아무것도 안 고르면 그 기본 목록이 그대로 뜬다.**

#### 3-1 붙인 것 (2026-09-16)

- `AuthContext.allowedMenus` — 로그인하면 `/menus/mine` 을 읽는다.
  **`null` 은 "아직 못 읽음"** 이고 빈 Set 이 "제한 없음" 이다. 읽기에 실패해도 빈 Set 으로
  끝낸다 — null 로 두면 요약 패널이 영영 호출을 미룬다
- 거르는 곳 4군데: 좌측 메뉴(`SideNav`) · 대분류 허브(`GroupPage`) · 상단 탭과 개수
  (`TopNav`·`navItemCount`) · 주소 직접 진입(`ScreenPage`). **한 곳만 걸면 나머지에 남는다**
- 대시보드 요약과 사이드바 출결은 **부르기 전에** `hasMenuCode()` 로 거른다.
  안 그러면 403 이 나고 "접근이 허용되지 않은 메뉴입니다" 가 빨간 경고로 뜬다 —
  열어준 적이 없을 뿐인데 고장으로 읽힌다
- 설정 화면은 사용자 관리 계정 목록의 **메뉴** 버튼(최고관리자만). 부모를 체크하면
  자식까지 함께 보낸다

### 지금 권한은 어디까지 막혀 있나

- **계정별 메뉴 노출** — 위 3-1. 화면에서 감추고, 서버가 API 단에서 403 을 준다
- **관리자 그룹** — 메뉴 숨김 + 주소 직접 진입 차단 (`/g/admin` · `/s/admin-*`)
- **조회 전용** — API 클라이언트에서 GET 아닌 요청을 끊는다
- 그 밖의 역할(담임이 상벌점을 줄 수 있는가 등)은 **손대지 않았다.** 추측이 되기 때문이다
