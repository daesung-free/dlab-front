# SCREEN_CONTRACT.md — 화면이 서버 값을 그대로 쓰지 않는 자리

`dlab-api/docs/frontend-contract.md` 의 **반대 방향** 문서다. 그쪽은 「서버는 이렇게
동작한다」를 적고, 이 문서는 **「화면은 이렇게 쓰고 있다」**를 적는다.

★ **왜 필요한가.** 2026-10-30 하루에 백엔드 전제가 두 번 어긋났다. 둘 다 서버 코드만
보고 세운 판단이었고, **화면이 하고 있는 일**이 빠져 있었다.

```
① 감사 로그 기간 상한   「화면이 1년으로 막고 있을 것」  → ★ 화면엔 상한이 없었다
② 장학과 할인          「서버에 참조가 0건이라 안 겹친다」 → ★ 화면이 둘을 한 필드에 싣고 있었다
```

②는 **돈이 틀리는 자리**였다. `discountCode` 가 들어오면 장학 70% 가 정책 10% 로
덮이고 **오류 없이 금액만 달라진다.**

## 적는 기준

**서버가 보낸 값을 그대로 쓰는 필드는 적지 않는다** — 그건 서버가 이미 안다.
적는 것은 **화면이 조립하거나 다른 뜻으로 채우는 자리**뿐이고, 각 줄은 둘을 말한다.

```
① 화면이 그 필드를 ★ 어떻게 채우는가
② ★ 서버가 그걸 모르면 무엇이 깨지는가
```

★ ②가 없으면 백엔드가 읽을 이유가 없다. 「`discountRate` 에 장학율을 넣는다」가 아니라
**「넣는다는 것을 모르면 정책 할인이 장학을 덮는다」**로 적는다.

---

## 1. 쓰기 — 화면이 값을 만들어 보내는 곳

### 1-1. ★★ `discountRate` · `discountSource` ← **장학**

`POST /admin/tuition-billings/monthly` (일괄). `PaymentStatus.tsx` `runBulk()`

```
listStudentScholarships(enrollmentId) 로 학생별 장학을 읽어
  discountRate   ← 장학의 discountRate
  discountSource ← 장학명(displayName ?? scholarshipType)
```

★ **장학과 청구의 연결을 서버가 아니라 화면이 하고 있다.** `domain/payment` 에
`Scholarship` 참조가 0건인 것은 맞지만, 겹침은 이미 일어나고 있다.

⚠️ **서버가 모르면**: `discountCode` 를 같은 요청에 넣는 순간 서버가 코드를 우선해
**장학 70% 가 정책 10% 로 바뀌고 근거도 정책 코드로 바뀐다.** 오류는 안 난다.
→ 2026-10-30 백엔드가 **장학생 + `discountCode` 를 400 으로 거부**해 막았다
(규칙이 정해지면 거부를 규칙으로 바꾼다). `API_GAPS.md` 46부.

⚠️ **아직 안 정해진 것**: 장학과 할인을 **합산하나 하나만 쓰나.** 합산이 정답이면
화면이 장학 하나만 쓰고 있어 **이미 발행된 청구가 덜 깎인 금액**이다.

### 1-2. `discountSource` 는 **발행 시점 스냅샷**이다

화면이 장학명을 박는 이유는 **나중에 장학이 취소돼도 근거가 남아야** 해서다.

⚠️ **서버가 모르면**: 서버도 여기에 정책 코드를 박으려 한다. **같은 칸에 둘이 들어갈 수
없다.** 무엇을 남길지 정해야 한다.

### 1-3. 공개 링크 주소는 **화면이 만든다**

`shareReservation()` 은 **토큰만** 준다. 주소는 `lib/publicUrl.ts` 가 만든다.

```
★ 관리자 도메인이 아니라 ★ 공개 도메인이다 (waitlistUrl · noticeUrl)
```

⚠️ **서버가 모르면**: 서버가 완성된 URL 을 주기 시작하면 **두 벌**이 되고, 관리자
도메인으로 만들어 주면 **학부모가 로그인 화면을 보게 된다.**

### 1-4. 일괄 처리 대상은 **화면이 체크한 것만** 보낸다

검색 조건을 보내 서버가 추리는 방식을 쓰지 않는다.

⚠️ **서버가 모르면**: 조건 기반 일괄 API 를 만들어도 화면이 안 쓴다. **데스크가 누구에게
나갈지 보지 못한 채 수백 건이 발행되는 것**은 되돌릴 수 없다.

## 2. 읽기 — 화면이 서버 응답을 다시 조립하는 곳

### 2-1. 결제 거래 목록은 **청구 × 결제로 펼친 것**이다

거래 목록 경로가 없어 `/receipt-status` 가 청구마다 주는 `payments[]` 를 펼쳐 쓴다.
`PaymentStatus.tsx` · `PaymentHistoryPrint.tsx`

```
★ 결제 없는 청구는 ★ 「미납」 행으로 따로 만든다 (서버에 그런 행은 없다)
★ paidAt 순으로 세우고, 미납은 맨 뒤로 보낸다
```

⚠️ **서버가 모르면**: 거래 목록 API 를 새로 만들 때 **「미납」이라는 행이 서버에 없다는
것**을 모른 채 설계한다. 학부모용 출력물이 그 행을 전제로 만들어져 있다.

### 2-2. ⚠️ 결제 내역 출력은 **학번으로 검색한 뒤 화면에서 한 번 더 거른다**

`/receipt-status` 에 학생 필터가 없어 `keyword` 로 학번을 검색하고, **그 결과를 다시
학번으로 거른다** — 검색이 느슨해 남의 행이 섞인다.

⚠️ **서버가 모르면**: 학부모에게 **다른 학생의 결제 내역이 찍힌 서류**가 나간다.
→ 학생 필터(`studentId`)가 생기면 이 두 겹을 걷어낸다.

### 2-3. ⚠️ `/receipt-status` 는 `year` 가 필수다 (`month` 가 아니다)

안 보내면 400 인데 **응답 `data` 가 비어 와서 「0건」으로 읽힌다.**

⚠️ **서버가 모르면**: 「조회했는데 없다」와 「파라미터가 틀렸다」가 화면에서 같아 보인다.
★ 상태코드를 먼저 봐야 하는 자리다.

### 2-4. 학원생 현황 — 네 칸은 **학생 목록으로 센다**

서버 반별 집계는 **재원만** 준다. `StudentStatus.tsx`

```
★ 반별 휴원·퇴원 · 반 안의 계열 · 계열 × 재수 구분  → 학생 목록으로 센다
★ 반별은 /classes 기준으로 합친다 — 서버 집계가 ★ 재원 0 인 반을 통째로 빼기 때문
```

⚠️ **서버가 모르면**: 집계에 상태별 인원을 더해 줄 때 **화면 계산과 두 벌**이 되고,
숫자가 어긋나도 오류가 안 난다. 재원 0 인 반이 **화면에서 사라지는** 것도 그 이유다.

### 2-5. 대기자 관리는 **지점을 화면에서 거른다**

`/admin/admission-reservations` 가 `academyId` 를 **안 받는다.**

⚠️ **서버가 모르면**: 파라미터를 추가해도 화면이 안 쓴다. 지금은 **거르지 않으면 분당
담당자가 대구 지원자에게 전화한다.**

### 2-6. 상담 기록 검색은 **전량을 받아 화면에서 거른다**

서버 검색 조건이 없어 반·이름·담임을 화면이 좁힌다. `ConsultLog.tsx`

⚠️ **서버가 모르면**: 그 엔드포인트에 **서버 페이징이 생기면 그날로 전제가 깨진다** —
화면은 전량이 손에 있다고 믿고 거르므로 **2페이지의 사람이 조용히 안 나온다.**

### 2-7. 약관 **필수/선택의 정본을 화면이 들고 있다**

`TERMS_CATALOG`(`src/api/appConfig.ts`) 가 디랩 입학동의서 최종본 기준 10종의
`required` 를 들고 있고, **그와 다르게 등록하려 하면 화면이 경고한다.**

⚠️ **서버가 모르면**: 서버가 정본을 바꿔도 화면 경고가 **거짓말**이 된다.
★ 정본이 바뀌면 이 상수도 같이 바꿔야 한다 — 알려 줘야 하는 자리다.

### 2-8. `effectiveAccounts` 가 **없으면 유효 비율을 말하지 않는다**

`TermsUsage.effectiveAccounts` 가 옵션이라, 없을 때 **0 으로 읽지 않는다.**

⚠️ **서버가 모르면**: 0 으로 읽으면 **전원이 다시 동의해야 하는 것처럼** 보인다.
그건 만료 안내가 아니라 **오보**다.
★ 그래서 **만료 개념이 없는 약관도 `agreedAccounts` 와 같은 값**으로 채워 달라고 요청했다
— 화면이 「이 약관은 만료가 있나」를 판단하면 코드가 화면에 박힌다.

### 2-9. 입학예약 첨부는 **순번으로 표시한다**

응답에 **원본 파일명과 종류가 없다**(홈페이지 수신 규격 `setStdFile` 에 자리가 없다).
그래서 「첨부 1」처럼 쓰고, **그게 화면 누락이 아니라고 화면에 적어 뒀다.**

⚠️ **서버가 모르면**: 파일명이 생겼을 때 **그 안내 문구가 남아** 거짓말이 된다.

### 2-10. ⚠️ 마스킹 — **응답 `masked` 를 읽는 화면이 셋뿐이다**

응답 `masked: true` 면 `phone`·`birthDate` 가 **이미 가려져** 온다(`2007-**-**`).
그러면 화면이 또 가려선 안 되는데, **실제로 그 값을 읽는 화면은 셋이다**(2026-10-30 확인).

```
★ 읽는다   StudentSearch · AffairsRoster · ProfileForm
⚠️ 안 읽는다  나머지 — DataTable 의 `masked` 토글만 보고 화면에서 가린다
            (응답 `masked` 는 7개 이상 모듈에 있다)
```

⚠️ **서버가 모르면**: 안 읽는 화면에서 **이중 마스킹**이 된다 — 서버가 `010-****-5678`
을 주고 화면이 다시 가려 **더 지워진 값**이 보인다. 지금 눈에 안 띄는 것은 그 화면들이
마스킹 대상 컬럼을 많이 안 쓰기 때문이고, **규칙이 지켜지고 있다는 뜻은 아니다.**

★ 우리 쪽 할 일이다 — 서버에 요청할 것은 없다. 여기 적는 이유는 **「프론트가 다 읽고
있다」고 전제하지 말아 달라**는 것이다.

### 2-11. 선택지를 **서버 목록으로 갈아끼우는 자리**

수정 이력의 업무 영역이 그 예다. 화면 하드코딩 8개 vs 서버 12개였고, **「반」에 실제
49건이 쌓여 있는데 거를 수 없었다** — 담당자는 기록이 안 되는 줄 알았다.
→ 2026-10-30 에 `listAuditAreas()` 로 갈아끼웠다.

⚠️ **서버가 모르면**: enum 에 값을 더해도 화면이 못 본다. ★ **목록을 주는 경로가
있으면 알려 주는 쪽이 낫다** — 화면이 들고 있는 상수는 반드시 뒤처진다.

## 3. 조용히 깨지는 집계 — 화면 필터가 서버 기준과 다른 곳

```
특강 확정자   ★ status=CANCELED 로 바뀌어도 waitlisted 는 false 로 남는다
             !waitlisted 로 세면 취소자가 섞여 서버 4명 · 화면 5명이 됐다(2026-09-16)
성적 백분위합  ★ 코드 목록이 학년·연도마다 다르다
             고3·N수 코드(INQUIRY1/2)만 갖고 있어 고2는 국어+수학만 더했다
```

⚠️ **서버가 모르면**: 요약 API 와 화면 숫자가 어긋나도 **오류가 안 난다.**
★ 새 집계를 줄 때 **「무엇을 세는가」를 한 줄 적어** 주면 화면이 대조할 수 있다.

---

## 4. 유지 규칙

- **화면이 조립을 그만둔 자리는 이 문서에서 지운다.** 남겨 두면 서버가 없는 전제를
  맞추려 한다.
- 새로 조립하기 시작하면 **그 PR 에서 여기 한 줄 더한다.** 나중에 적으려 하면 안 적는다.
- ★ **「서버에 없다」고 적을 때는 확인한 날을 쓴다.** 서버는 매주 바뀐다 —
  `CLAUDE.md` 4항이 그 이유로 한 번 틀렸다.
